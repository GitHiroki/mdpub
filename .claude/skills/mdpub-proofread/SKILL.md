# mdpub 文章校正

mdpub の「深掘り」「Q&A」ドキュメントを読みやすくするための校正ワークフロー。
土台となる文章規範は別スキルに置き、ここではそれを読み込んだうえで mdpub 固有の規範を上乗せする。

対象は `src/content/docs/` 配下の Markdown（深掘りメモ、Q&A、TL;DR 付き技術メモなど）。

## ワークフロー

### Step 1: 文章規範を読み込む

作業前に、土台となる規範を必ず読む。

```
.claude/skills/japanese-tech-writing/SKILL.md
```

（このスキルから見た相対パスは `../japanese-tech-writing/SKILL.md`。）

全節に従うが、深掘り/Q&A の校正では特に次を重視する。

- **段落と論証の構成**（パラグラフライティング、一段落一トピック、結論は一度だけ）
- **論証の厳密さ**（推量を機械的に断定へ変えない、別物を「同じ」とまとめない、因果は機構を一文で）
- **冗長の排除**（同じ主張を言い換えて繰り返さない、中間段階は省く）
- **LLM っぽい表現の禁止**（「重要なのは〜」「掘り下げる」「多角的」等の空句を使わない）

### Step 2: 校正対象を特定する

校正する `src/content/docs/**/*.md` を確定する。ユーザーが指定していなければ確認する。
複数ファイルが対象のときは 1 ファイルずつ進める。

### Step 3: mdpub 固有の読みやすさ規範を適用する

Step 1 の規範に加えて、深掘り/Q&A 形式に特有の次の点を整える。

- **Q&A は「問い → 結論 → 根拠」の順を保つ。** 結論を先頭に置き、根拠を後ろに回す。
  `**Q1. 〜？**` → `→ 結論` → 箇条書きの根拠、という既存の型を崩さない。
- **セクションの塊は 1 論理単位に保つ。** `TL;DR` / `論点と結論` / `理解したこと` /
  `次回の宿題` のような構造を尊重し、塊をまたいで話題を混ぜない。
- **TL;DR は結論だけを短く。** 本文の要約の言い直しを並べず、各行を一つの結論にする。
- **整形は土台の規範に従う。** 一文一行、コード/差分/ログはコードブロック、
  並列の中黒（・）は避ける、用語と定義の箇条書きは全角コロン「**用語**：説明」。
- **frontmatter は壊さない。** `title` / `description` / `sidebar.badge` を勝手に変えない。
  特に `badge`（`info` / `新規` / `更新`）はバッジ管理（mdpub-deploy）の領域なので触らない。
- **「深掘り」という語の扱い。** 土台の規範は空虚な動詞「深掘りする」を禁止するが、
  mdpub では「深掘り」はページ/セクションの**種別ラベル**（例: `OKF深掘り`）として使われる。
  見出し・タイトルのラベルとしての「深掘り」は残してよい。地の文での空虚な動詞用法
  （「ここで深掘りする」など中身を示さず終わるもの）だけを是正する。

### Step 4: 差分を提示して合意を取る

校正は内容の改変や誤読を招きやすい。変更点をユーザーに見せ、意図がずれていないか確認する。
論証の筋を変える編集（段落の再配置、削除、結論の言い換え）を含む場合は、特に明示して合意を取る。

### Step 5: デプロイ連携

合意できたら、公開まで進めるか確認する。

- **公開まで進める場合**: `mdpub-deploy` スキルに従う
  （バッジ更新スクリプト → commit → push → GitHub Actions が Starlight をデプロイ）。
  バッジ判定はスクリプトに任せ、モデルが diff を解釈して badge を書き換えない。
- **校正のみで止める場合**: ファイル編集までで終え、デプロイはしない旨をユーザーに伝える。

## 注意事項

- このスキルは「より自然にする」ためではなく、深掘り/Q&A の論理を読者が追えるようにするために使う。
- 局所的な差分の言い換えに終始せず、段落が前後の論理に対して果たす役割を見る。
- 規範文書（japanese-tech-writing）の語句は改変しない。校正対象は `src/content/docs/` のドキュメントのみ。
