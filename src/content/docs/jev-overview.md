## 一言でいうと

**文脈から意味を読む判断はJev、正確さが必要な計算や最終決定はコード。**

Jevは、文章を生成しないAIです。
ソフトウェアが直接使える「判断」を、型と確率つきで返します。
TypeSafe AIが2026年9月15日に公開しました。

## 基本の仕組み

- **入力**：`state`（判断対象と文脈）と、型付きの`questions`
- **出力**：質問ごとに、次の3種類の型で返る

| 型 | 聞くこと | 返るもの |
|----|---------|---------|
| Noul | はい / いいえ | 「はい」の確率（0〜1） |
| Choice | 候補のどれか | 選択肢、候補ごとの確率、confidence |
| Score | 定義した段階のどこか | 段階の期待値、確率、legend、confidence |

- 1つのstateに複数の質問をまとめて送ると、並列に評価される（質問同士は独立していて、互いの答えを参照しない）
- 応答は70〜500ms程度。入力100万トークンあたり0.042ドルで、出力は無料（いずれもベンダー公表値）

## 理解の道筋

### Q1. Structured OutputsでもLLMは型付きJSONを返す。Jevは何が違う？

**最初の理解**：はい/いいえで返したり、答えが合っている確率を返したりするところ？

**ズレていた点**：Noulの`0.8`は「**はい、である確率**」です。
「答えが正しい確率」ではありません。

**校正（calibration）とは**：0.8と出た事例を100件集めたとき、約80件で実際に「はい」になる、という集団としての性質です。
1件ごとの正しさは保証しないので、確率やconfidenceが高い1件でも外れることはあります。

### Q2. LLMに出させた`0.8`と、Jevの`0.8`は何が違う？

**気づき**：LLMの`0.8`は数値ではなく、推論して書いた**トークン**だ。

- **LLMの0.8**：「0」「.」「8」を、それっぽく書いた文章の続き。自信度を測った結果ではない
- **Jevの0.8**：あらかじめ固定した候補の上に乗った確率分布そのものが出力。分類器の最後に出る確率に近いイメージ（ただし内部の層構造は非公開）

**補足**：LLMの内部にも、次のトークンを選ぶ確率（logprobs）があります。
ただしGPT-4のテクニカルレポートでは、事前学習直後はよく校正されていたこの確率が、RLHF後に崩れたと報告されています。

### Q3. RLHFの共同発明者が、なぜRLCDという別の学習法を作った？

**最初の理解**：生成LLMだと正確じゃないし遅かったから？

**整理**：速さと確率の正直さは**別の軸**です。

| 軸 | どこから来るか |
|----|--------------|
| 速さと安さ | 構造。トークンを逐次生成せず、固定候補を並列に評価する。長文を書かないので出力が安い |
| 確率の正直さ | 学習法（RLCD）。報酬を「人に好まれること」から「確率が実際の結果と合うこと」に置き換えた |

アプリはJevの確率を「0.8未満なら人に回す」のようなしきい値に使います。
しきい値は「0.8なら8割方は当たる」ことを前提に引いた線なので、確率が実際の結果とずれていれば、人に回すべき事例を正しく選べません。
ソフトウェアに使わせる確率では、人に好かれることより、実際の結果と合うことが優先されます。

### Q4. 位置づけは？

**自分の言葉で**：汎用だが遅いLLMから「判断」だけを抜き出して速くやらせ、その後のLLMやアプリを助ける位置。→ その通り。

TypeSafeが掲げる「System One Models」という名前は、カーネマンの「速い思考」から来ています。

- **LLM = System Two**（じっくり考える）
- **Jev = System One**（反射的に判断する）

組み合わせ方の例：

- **前段**：問い合わせの振り分け。必要なものだけLLMに回す
- **後段**：エージェントの出力や実行しようとしているコマンドの検査（ガードレール）。危険度などを小さな質問に分けて採点させ、許可するかどうかのポリシーはコードが持つ

### Q5. 「5個の果物」に「5個より多いか？」と聞くと0.88。なぜ？

**最初の理解**：質問を独立して評価することと関係ある？ → 関係ない。

**原因**：Jevは**数えていない**と考えられます。
意味の上で「たくさんある感じ」かどうかを判断しているだけで、5と6の境界を厳密に判定する仕組みを持たないためです（内部構造は非公開なので、挙動からの推定）。

**System Oneらしい弱点**：カーネマンの例に「バットとボールで1.10ドル、バットはボールより1ドル高い。ボールはいくら？」があります。
直感は「10セント」に飛びつきますが、正解は5セントです。
速い直感的な判断は、もっともらしい答えを出す代わりに、正確な計算を省きます。

**設計での避け方**

- 個数、金額、日付の比較はコードで計算して、結果をstateに入れる
- Jevには「返金要求か」のような意味の判断だけを聞く
- 反対向きの2問（「〜か」「〜でないか」）は独立に評価されるので、確率の合計が1になる保証はない。1問にしてコードで条件を管理する

## 使う / 使わないの目安

| 場面 | 判断 |
|------|------|
| 問い合わせの担当部署振り分け | 向いている（Choice + 低confidenceは人へ） |
| ポリシー該当の判定 | 候補（意味判断はJev、権限や最終アクションはコード） |
| 感情の強さや品質の段階評価 | 候補（Score + 正解データで評価） |
| 長文生成、根拠の説明 | LLMを使う |
| 画像、音声、動画 | 直接は扱えない |
| 個数、金額、日付の厳密な計算 | コードで処理する |

## 過去の学びとのつながり

- **「決定的な出力はモデルではなくスクリプトへ」**（スキル設計とセキュリティスキャンで確認済みの原則）：Jevの「計算はコード、判断はJev」は、この原則をモデルの設計そのものに組み込んだ形
- **「モデルの自己説明は仮説レベル」**：LLMに書かせた自信度`0.8`も、自己説明と同じく測定ではなく生成された文章。信頼できる確率が欲しければ、生成とは別の仕組み（logprobs、あるいはJevのような校正済み分布）が必要
- **セキュリティスキャンの階層化**（曖昧な評価はモデル、構造チェックは決定的スクリプト）：Jevを入れるなら、「曖昧な評価」の層を高速かつ安価に置き換える候補になる
